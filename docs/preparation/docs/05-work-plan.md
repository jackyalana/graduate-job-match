# 开发任务与论文证据计划

先把原系统跑通，再依次做权限与数据、匹配算法、投递闭环和评估。每阶段都留下可重跑证据，避免最后再补一套与系统行为不同的论文描述。下列任务是顺序与范围，不是未经验证的工期承诺。

## 1 开发顺序

| 阶段 | 任务 | 主要输出 | 依赖 |
| --- | --- | --- | --- |
| M0 | 来源锁定、许可证、环境、上游启动、API 映射、复用评估 | BASELINE、REUSE_MATRIX、M0_REPORT、初始证据 | 准备包 |
| M1 | 数据迁移、DTO、角色和对象权限、学生画像、岗位资格与审核 | DDL、字典、OpenAPI、权限测试、页面 | M0 审核通过 |
| M2 | 批量候选、内容评分、解释、兜底、缓存版本与分页 | 算法纯函数、黄金样例、匹配页面、推荐接口 | M1 |
| M3 | 收藏与隐藏、行为记录、投递快照、状态机、附件与统计 | 完整三角色端到端流程、并发和越权测试 | M2 |
| M4 | CF、统一评估、性能、部署与交付 | 实验报告、评估脚本、测试证据、演示录像 | M3 |

## 2 每阶段证据目录

```text
docs/evidence/
  M0/
    environment.txt
    commands-and-exit-codes.md
    backend-tests.log
    frontend-build.log
    smoke-results.json
    screenshots/
  M1/ ... M4/
evaluation/
  README.md
  config/
  fixtures/
  output/<run-id>/
    manifest.json
    metrics.json
    metrics.csv
    report.md
```

run-id 仅用于保存实验，不用于制造多个挑选性结果。manifest 记录提交、算法版本、数据哈希、种子、时间切分、配置、运行环境和执行命令。报告注明哪些测试确实跑过、哪些没有跑过。

## 3 论文中的实现贡献

可据实描述的工作方向：将通用招聘流程适配到毕业生画像；设计学历与毕业年份资格检查；实现多维可解释内容匹配；为稀疏行为设置动态融合权重；完善投递快照、状态机和权限；建立可复现评估及冷启动对比。

这些属于系统设计、工程实现与应用改进方向，不预先宣称新的推荐算法、首次提出或显著优于所有方法。若余弦、协同过滤来自已有方法或代码，应在相关章节与代码来源表中注明。

建议论文结构与证据对应如下，具体章节服从学校模板：

| 章节 | 内容 | 必需证据 |
| --- | --- | --- |
| 绪论 | 就业信息与匹配问题、目标和边界 | 正式文献与需求分析，不能用源码卖家文案替代 |
| 相关技术 | Spring Boot、Vue、MySQL、内容匹配和 CF | 实际使用版本、权威文献、算法定义 |
| 需求分析 | 三角色用例、功能/非功能需求 | FR 编号与验收表 |
| 系统设计 | 架构、ER、状态、API、权限 | 与最终 schema 和实现一致的图与说明 |
| 核心实现 | 画像、过滤、打分、冷启动、快照 | 源码位置、运行样例和关键接口 |
| 测试与实验 | 功能、权限、并发、性能、推荐评估 | 真正执行的日志、配置、数值、截图与局限 |
| 总结 | 已完成范围与不足 | 有限数据、冷启动偏差、后续真实验证计划 |

## 4 建议答辩演示

1. 管理员审核一家模拟企业和一个模拟岗位，解释谁能看到未审核内容。
2. 学生新账号未填画像时看到热度兜底，页面明确不显示伪造匹配分。
3. 填写技能、意向城市和岗位类别，展示匹配明细及缺失技能。
4. 修改一项偏好，刷新推荐，解释为什么得分变化以及旧批次为何失效。
5. 投递后企业查看该份快照，邀请面试、发出录用，学生接受；展示状态时间线。
6. 尝试用另一个企业读取投递，显示被拒绝；展示测试与实验报告，解释数据范围。

## 5 交回审核者的简短消息模板

```text
阶段：M0 / M1 / M2 / M3 / M4
代码位置或仓库：
分支与完整 SHA：
相对上次审核的改动：
报告和证据路径：
启动方式与当前地址：
已运行的测试及结果：
失败或跳过项：
偏离 SDD 的地方：
请基于实际代码与证据审核，不要仅根据此消息判定通过。
```

当前审核聊天收到可访问代码和证据后可逐阶段审核；本准备包没有创建其他聊天、启动实施代理或设置后台自动监控。
