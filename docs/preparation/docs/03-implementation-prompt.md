2. 记录 Java、Maven、Node、npm、MySQL、Redis 的实际可用情况，检查 pom、lockfile、配置、启动脚本和数据库 SQL。不要盲目升级全部依赖，也不要用跳过测试伪装通过。

## M0 通过后的实施约束

- 严格遵照 SDD 的角色、硬过滤、评分公式、缺失值定义、状态机、数据归属、快照、缓存版本和评估切分。需要变更先提交具体 ADR 和影响，不偷偷改需求。
- M1 完成数据与权限，M2 完成内容匹配和冷启动，M3 完成投递闭环，M4 完成协同过滤、评估、完整测试和交付。每个阶段先自测，再提交审核。
- 保留 Vue 3 页面、公共布局和基础 CRUD，尽量用增量迁移。旧接口只能调用同一业务规则，不能成为绕过新规则的入口。
- 推荐和匹配分从后端计算，不允许随机数、静态 JSON 或前端 mock 冒充真实功能。demo 合成数据可以使用，但必须明确标注。
- 初版核心流程不依赖 LLM、收费服务或真实招聘站爬虫。不要扩大到聊天、支付、微服务和多租户。
- 已投递简历、岗位、评分保存快照；HR 仅访问投向本人岗位的记录。归档岗位不得物理删除历史投递。对象归属校验和并发约束必须有真实测试。
- 无有效数据时正确返回资料提示和兜底，不显示伪造匹配概率。推荐不足 K 时返回实际数量，不能补无效岗位。
- 必须提供热门、内容和混合算法对比；如结果无提升或仅有合成数据，照实报告，禁止杜撰准确率、就业率或用户满意度。
- 代码来源写入 THIRD_PARTY_NOTICES，保留 MIT 版权与许可。论文贡献说明区分原项目、改造内容、使用的 AI 辅助，不包装为全原创。

## 每次交给审核 AI 的结果格式

1. 阶段名称、状态、项目绝对路径或可访问仓库链接、分支和 commit SHA、工作区是否干净。
2. 已完成需求编号与对应代码位置；相对上次审核的改动清单。
3. 实际执行的测试和构建命令、环境、退出码、失败与跳过项。运行日志放 docs/evidence/，敏感内容脱敏。
4. 可运行的启动命令、访问地址、仅用于 demo 的账号获取方式；浏览器截图/录像和 API 样例。
5. 数据迁移、恢复方式、接口变更和依赖变更。
6. 已知风险、未完成项、偏离 SDD 的提案。
7. 明确写“待审核”，不要替审核者声明最终通过。
