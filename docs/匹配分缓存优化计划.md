## 先回答：match_score 记录什么时候会被用上
- 当前代码里，match_score 只在 [MatchServiceImpl.computeAndSave](file:///Users/bytedance/java/lan-recruitment/backend/src/main/java/com/lanrecruitment/service/impl/MatchServiceImpl.java#L32-L55) 被“用上”一次：先 `selectOne(resumeId, jobId)` 判断是否存在，再 `insert/update`。
- 推荐/HR排序并不会“查询 match_score 来排序”，而是每次循环现算分数，然后在内存里 sort：
  - 用户侧推荐：[JobBrowseServiceImpl.recommend](file:///Users/bytedance/java/lan-recruitment/backend/src/main/java/com/lanrecruitment/service/impl/JobBrowseServiceImpl.java#L91-L158)
  - HR投递排序：[HrJobServiceImpl.listApplications](file:///Users/bytedance/java/lan-recruitment/backend/src/main/java/com/lanrecruitment/service/impl/HrJobServiceImpl.java#L282-L307)
- match_score 还会在数据变更/清理时被删除（岗位物理删除、岗位标签更新、管理员删用户/HR）。

## 目标
- 做一套“匹配分缓存”让 computeAndSave 真正复用历史计算结果。
- TTL 为代码静态常量。
- 通过配置 `lan.match.cache.store=memory|redis` 切换实现（键前缀按 lan:... 规范）。
- 当简历标签/岗位标签变化时，自动失效相关缓存，下一次请求强制重算。

## 设计与实现步骤
### 1) 抽象缓存层
- 新增接口 `MatchScoreCache`：
  - `BigDecimal get(Long resumeId, Long jobId)`
  - `void put(Long resumeId, Long jobId, BigDecimal score)`
  - `void invalidateByResume(Long resumeId)`
  - `void invalidateByJob(Long jobId)`
- 静态常量：
  - `TTL_SECONDS`（过期时间）
  - `KEY_PREFIX = "lan:recruitment:match:"`

### 2) 内存实现（memory）
- `InMemoryMatchScoreCache`：
  - `ConcurrentHashMap<pairKey, Entry(score, expireAt)>`
  - 维护双向索引以支持快速失效：`resumeId->Set<jobId>`、`jobId->Set<resumeId>`
  - `get` 进行惰性过期清理，`invalidateBy*` 通过索引删除相关 pair。

### 3) Redis 实现（redis）
- 新增 `RedisClient`：基于 `StringRedisTemplate` 做简单封装（get/setEx/del/sadd/smembers/srem/expire）。
- `RedisMatchScoreCache`：
  - pair key：`lan:recruitment:match:score:{resumeId}:{jobId}` -> score 字符串（BigDecimal.toPlainString）+ TTL
  - 索引集合：
    - `lan:recruitment:match:resume:{resumeId}`（Set jobId）
    - `lan:recruitment:match:job:{jobId}`（Set resumeId）
  - `put`：写 pair + 维护两侧索引并刷新索引 TTL。
  - `invalidateByResume/job`：通过索引集合拿到关联 id，批量删 pair key，并清理集合（必要时做 SREM 清理对侧集合）。

### 4) 配置切换（仿照 SaTokenDaoStoreConfig）
- 新增 `MatchScoreCacheConfig`：
  - `@ConditionalOnProperty(prefix="lan.match.cache", name="store", havingValue="redis")` -> 注入 RedisMatchScoreCache
  - `@ConditionalOnProperty(prefix="lan.match.cache", name="store", havingValue="memory", matchIfMissing=true)` -> 注入 InMemoryMatchScoreCache
- application.yml / application-dev.yml 增加：
  - `lan.match.cache.store: memory`（或 dev 环境改 redis）

### 5) 接入算法核心（让缓存生效）
- 改造 `MatchServiceImpl.computeAndSave`：
  1) 先查 `matchScoreCache.get(resumeId, jobId)`，命中直接返回（避免再次查库加载向量/计算）。
  2) 未命中则按现有逻辑加载 `resume_tag/job_tag`、计算余弦相似度。
  3) `matchScoreCache.put` 后，再执行现有 `match_score` upsert（保持落库能力）。

### 6) 标签变化触发重新匹配（失效策略）
- 简历标签保存：`ResumeServiceImpl.saveTags`
  - 保存后：`matchScoreCache.invalidateByResume(resumeId)`
  - 同时 `matchScoreMapper.delete(resume_id=...)`（避免未来如果开始读 match_score 排序时出现旧分数）。
- 岗位标签保存：`HrJobServiceImpl.saveJobTags`
  - 保存前/后：`matchScoreCache.invalidateByJob(jobId)`
  - 保留现有 `matchScoreMapper.delete(job_id=...)`。
-（可选）简历删除、岗位 remove 等路径同样做 invalidate，保证一致性。
