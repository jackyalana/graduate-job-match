## 文档目标

本文档对本项目“简历-岗位匹配 / 岗位推荐 / HR 投递筛选排序”的核心算法与工程链路做详细说明：数据如何产生、特征如何表达、分数如何计算、如何缓存与失效、以及哪些接口会触发匹配计算。

相较于 README 的简述，本文更偏“实现级”说明，便于你在此基础上继续扩展（例如：引入更复杂的召回/排序策略、离线预计算等）。

核心计算代码：`backend/src/main/java/com/lanrecruitment/service/impl/MatchServiceImpl.java`

---

## 1. 数据模型（画像来源）

系统的匹配算法以“标签体系”为基础，将简历和岗位都抽象成稀疏向量 `{tagId -> weight}`。数据来源主要有三类表：

### 1.1 标签库：tag

`tag` 表提供统一标签集合与基础权重：

- `tag_type`：标签类型（如 SKILL / INDUSTRY / EXPERIENCE）
- `base_weight`：标签基础权重，用于向量权重计算

表结构见：`backend/sql/init.sql` 中 `tag` 定义。

### 1.2 简历画像：resume_tag

`resume_tag` 表存储某份简历选中的标签、熟练度与最终权重：

- `resume_id`
- `tag_id`
- `proficiency`（技能类标签使用）
- `weight`（匹配使用的最终权重）

简历标签保存入口：`/api/user/resume/tags/save`，实现位于 `ResumeServiceImpl.saveTags`。

权重策略（实现级）：

- 若标签类型为 SKILL：`weight = base_weight * proficiency`
- 否则：`weight = base_weight`（proficiency 置空）

### 1.3 岗位画像：job_tag

`job_tag` 表存储某个岗位的标签、熟练度与最终权重（与简历同形）：

- `job_id`
- `tag_id`
- `proficiency`（技能类标签使用）
- `weight`（匹配使用的最终权重）

岗位标签保存入口：`/api/hr/job/tags/save`，实现位于 `HrJobServiceImpl.saveJobTags`。

权重策略与简历侧一致：

- SKILL：`weight = base_weight * proficiency`
- 非 SKILL：`weight = base_weight`

## 2. 特征表达（向量构建）

匹配计算会从 `resume_tag` 与 `job_tag` 加载稀疏向量：

- 简历向量：`resumeVec = Map<tagId, weight>`
- 岗位向量：`jobVec = Map<tagId, weight>`

实现细节：

- 若 `weight` 为空按 0 处理
- 仅使用 `tagId -> weight` 做匹配，当前不会使用“教育/城市/期望薪资”等结构化字段参与相似度计算

对应实现：

- `MatchServiceImpl.loadResumeVector`
- `MatchServiceImpl.loadJobVector`

---

## 3. 匹配度计算（余弦相似度）

匹配分数使用余弦相似度：

`score = dot(a,b) / (||a|| * ||b||)`

其中：

- `dot(a,b)`：仅在共有 tagId 上累加 `a[tagId] * b[tagId]`
- `||a||`、`||b||`：各自向量的 L2 范数

实现级边界处理（非常重要，会影响“为什么全是 0”）：

- 任一向量为空：返回 `0.0000`
- 任一范数为 0：返回 `0.0000`
- 计算结果 NaN/Inf/负数：归零
- 最终保留 4 位小数（HALF_UP）

对应实现：`MatchServiceImpl.cosine`

---

## 4. 结果落库：match_score（含索引）

计算得到的 `(resumeId, jobId) -> score` 会写入 `match_score` 表（upsert 逻辑）：

- 存在记录：更新 `score` 与 `created_at`
- 不存在记录：插入新记录

`match_score` 表定义在 `backend/sql/init.sql` 中，并包含与排序相关的索引（如 `(resume_id, score)`、`(job_id, score)`）。

注意：本项目目前不会“用 SQL 按 score 排序”完成推荐分页；排序发生在 Java 内存中。match_score 的主要价值是作为二级缓存（见第 6 节）与结果留痕。

## 5. 端到端链路（哪些接口会触发匹配）

### 5.1 用户侧：岗位推荐（简历 -> 岗位列表）

接口：`GET /api/user/job/recommend`

推荐流程（实现级概括）：

1) 选择用于推荐的简历（传参 resumeId 或默认/最近简历）
2) 生成候选岗位集合（状态、审核、关键词/城市/类型/标签过滤等）
3) 冷启动兜底：无可用简历则随机返回候选岗位
4) 对候选岗位逐个计算匹配分（调用 `MatchService.computeAndSave`）
5) 按 `matchScore desc, jobId desc` 在内存排序
6) 分页截断返回（默认候选上限 200）

对应实现：`JobBrowseServiceImpl.recommend`

### 5.2 HR 侧：投递列表匹配排序（岗位 -> 简历列表）

接口：`GET /api/hr/job/applications?jobId=...`

流程（实现级概括）：

1) 拉取该岗位的投递记录
2) 对每条投递计算“投递简历 vs 当前岗位”的匹配分（调用 `MatchService.computeAndSave`）
3) 按 `matchScore desc` 在内存排序返回

对应实现：`HrJobServiceImpl.listApplications`

## 6. 匹配分二级缓存（L1 memory/redis + L2 match_score）

### 6.1 缓存目标与原则

目标：减少重复计算、减少对 `resume_tag/job_tag` 的重复查询，同时保持“标签变化后下一次必然重算”的一致性。

原则：

- 不改变接口语义与返回结果（用户视角无差异）
- 命中缓存时不再进行向量加载/余弦计算
- 标签变化时同时清理缓存与 match_score，保证不会返回旧分数

### 6.2 L1：可切换的缓存介质（memory / redis）

缓存抽象：`MatchScoreCache`，以 `(resumeId, jobId)` 为粒度读写 score。

配置开关：

- `lan.match.cache.store=memory|redis`

TTL：

- 使用静态常量定义，见 `MatchScoreCacheConstants.TTL_SECONDS`

Redis key 规范：

- key 前缀：`lan:recruitment:match:`
- score key：`lan:recruitment:match:score:{resumeId}:{jobId}`
- 反向索引（用于按 resume/job 批量失效）：`lan:recruitment:match:resume:{resumeId}`、`lan:recruitment:match:job:{jobId}`

Redis 客户端封装：`RedisClient`（基于 `StringRedisTemplate`）。

### 6.3 L2：数据库 match_score 作为二级缓存

`MatchServiceImpl.computeAndSave` 采用如下读取顺序：

1) 先查 L1（MatchScoreCache）：命中直接返回
2) L1 未命中查 L2（match_score 表）：命中则回填 L1 并返回
3) 两者都未命中：加载向量、计算余弦相似度、写入 L1 并 upsert match_score

这样即使 L1 过期、服务重启或 Redis 清理，仍可复用历史分数，降低“重复计算成本”。

## 7. 失效策略（保证标签变化后重新匹配）

匹配分是否“过时”，在本项目中由“标签是否变化”决定。为避免旧分数影响推荐，采取主动失效：

### 7.1 简历标签变化

当调用 `ResumeServiceImpl.saveTags` 保存简历标签时：

- 删除该简历关联的 `match_score`
- 失效该简历相关的 L1 缓存（按 resumeId）

简历删除时也做同样清理。

### 7.2 岗位标签变化

当调用 `HrJobServiceImpl.saveJobTags` 保存岗位标签时：

- 删除该岗位关联的 `match_score`
- 失效该岗位相关的 L1 缓存（按 jobId）

岗位物理删除（remove）时同样清理。

## 8. 常见问题与排查

### 8.1 为什么推荐分经常是 0？

常见原因：

- `job_tag` 未配置或保存失败，导致岗位向量为空
- `resume_tag` 为空（用户未设置简历标签或保存失败）
- 权重都为 0（base_weight/proficiency 异常）

排查路径：

- 查看 `resume_tag` / `job_tag` 表是否有对应记录与 weight
- 触发一次推荐/HR投递排序，看 `MatchServiceImpl.loadResumeVector/loadJobVector` 是否能加载到非空向量

### 8.2 命中缓存会不会导致返回旧分数？

不会。因为标签变化时会同时：

- 删除 match_score（L2）
- 失效 L1 缓存（memory/redis）

下一次请求必然走到“重新计算”分支。

## 9. 后续可扩展方向（不影响现有实现）

- 将推荐排序从“内存排序”改为“SQL 按 match_score 排序分页”，利用索引提升分页性能
- 引入离线/异步预计算（例如：标签变化后预计算 topN）
- 在相似度之外融合业务特征（城市、薪资、工作年限、岗位热度等）做加权排序
